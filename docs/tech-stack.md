## ADR-001 引擎：Godot 4.x

**歷史決策，已由 ADR-009 取代。** Godot 原型已自工作區移除，可從 commit `cd32f57` 取回。

**上下文**：單人開發、目標平台 Windows、開發機是 Intel Arc 140V 內顯（16GB 共享記憶體）＋ 8 執行緒、專案必須是開源可審計的、場景是城市尺度低多邊形。

**決定**：Godot 4.x 標準版（非 .NET），主要用 GDScript。

**否決的方案**：

| 方案 | 為什麼否決 |
|---|---|
| **Rust + Bevy** | 沒有編輯器 → 擺一個門框要寫 40 行程式。缺動畫混合樹（喪屍的走/跑/攻擊/受擊/死亡上半身混合是核心體驗）、缺內建導航網格烘焙、城市串流與 LOD 全靠自己寫。素材生態極薄。這個專案真正的成本是**內容迭代速度**，Bevy 把成本壓在錯的地方。 |
| Rust + Fyrox | 有編輯器，但社群與 3D 功能落後一個世代，卡住時沒人可問。 |
| Unity | 迭代最快、素材最多，但**非開源**，與專案目標直接衝突；授權條款歷史上反覆過。 |
| Unreal 5 | Nanite/Lumen 天生適合城市，但 Arc 140V 內顯跑 UE5 是折磨（編譯、著色器、預覽都慢），且非開源。若日後有獨顯＋團隊，可重評。 |

**代價（已知並接受）**：大世界串流要自己寫 chunk 管理；沒有內建的「城市級」工具。

## ADR-002 座標系

- 右手座標、**Y 軸向上**、單位**公尺**、區域 ENU 平面。
- 原始地理資料保留來源座標系與可追溯的地理資訊；轉換為引擎座標時，以所選上海街區的參考點建立局部平面座標，並記錄轉換方法。
- 距原點超過 ±4 km 時做 origin rebasing（單精度浮點抖動）。
- 多邊形一律以**逆時針（CCW）** 儲存（數學慣例），由烘焙器轉成引擎需要的繞序。

局部座標便於渲染與數值計算，不會使真實街區變成虛構地圖，也不能替代對來源授權與適用規範的核對。

## ADR-003 資料與渲染分離

```
原始地理資料 ──(tools/ 離線轉換及烘焙)──▶ 遊戲資料 ──▶ 遊戲引擎
   保留來源與座標資訊                         產物可重新生成
```

- 引擎**只讀烘焙產物**：不解析 OSM、不連網、不呼叫任何地圖 API。
- 換引擎不用重做資料；LOD 可重烘；每一筆素材來源可審計。

## ADR-004 分塊（Chunking）

以下為原 Godot 方案的規劃，尚未在目前 Three.js 原型中實作或驗證。

- **250 m × 250 m** 一格。
- 每格 = 1 個合併 mesh（按材質分 submesh）＋ 1 個 `NavigationRegion3D` ＋ 1 個簡化碰撞 ＋ 1 張生成表。
- 同時載入半徑 2 格（1 km × 1 km），其餘用 impostor／低模。
- **最佳化順序：Draw call ＞ 三角形數。** 內顯對 draw call 更敏感。

## ADR-006 什麼時候才引入 Rust

以下為原 Godot 方案的備註；目前 Web 原型不引入 Rust。

**觸發條件**（先到者）：
- 離線烘焙單次超過 60 秒；
- 需要執行期高效能模組：大規模尋路、上千單位群體模擬。

**手段**：用 [godot-rust (gdext)](https://github.com/godot-rust/gdext) 寫 GDExtension 模組，**不是**重寫遊戲。

在此之前一律用 Python。這個規模（一個街區幾千棟樓）Python 幾秒就跑完，提早最佳化只是換一種方式拖延。

## ADR-007 評估：TypeScript + Three.js（Web 技術棧）

**歷史評估，已由 ADR-009 更新為採用。** 下述技術選項與效能數字是先前的設想，不代表現有依賴或實測結果。

若採用，技術棧為：`Vite + TypeScript + three + @dimforge/rapier3d + recast-navigation-js + zod`

### 它強在哪（針對本專案）

- **城市資料管線**：GeoJSON／OSM 解析、`earcut` 三角化、LOD 生成，全在 TS 生態內。而且烘焙器與執行期**共用同一份 Zod schema 與型別**——用 Godot 就得在 Python 和 GDScript 之間手動維護兩份。
- **迭代速度**：Vite HMR 亞秒級。
- **發佈**：瀏覽器＝一個連結、零安裝、GitHub Pages 免費。對「免費開源遊戲」這個目標是最優解。
- **UI**：HTML/CSS。背包、暫停、設定用 DOM 寫，比任何引擎的 UI 系統都快。
- 全鏈路 MIT。

### 它弱在哪

- **沒有編輯器**，關卡＝資料＋程式。本專案已資料驅動，衝擊可控，但仍需自寫一個極簡擺放工具。
- **沒有 Steam 直通車**：要 Tauri（約 10 MB，剛好用到 Rust）或 Electron 包一層。
- **效能天花板低於原生**：iGPU 上必須嚴格控制動態光源與骨骼動畫數量。
- 生態是**圖形庫**不是**遊戲引擎**：導航網格、地形、存檔、粒子編輯器都要自己接。

### 效能現實（Arc 140V，1080p）

| 項目 | 判斷 |
|---|---|
| 低多邊形城市 5–20 萬三角形 | 不是問題 |
| Draw call | **真正的成本**。`BatchedMesh` 合批＋區塊合併，目標 < 60 |
| 動態光源 | 上限 1–2 盞（一把手電筒），其餘烘焙進頂點色／lightmap |
| 陰影 | 單一方向光＋CSM，或全烘焙 |
| 骨骼動畫 | 30 m 內 20–40 隻；更遠用 impostor 或 GPU 頂點動畫。200 隻 skinned mesh 一定掉幀 |

### 切換成本

因為 ADR-003（資料與渲染分離）成立，**前三個月的引擎選擇是可逆的**：`data/` 不動，換掉 `web/` 就行。

### 重評條件（先到者）

- 需要 **> 100 隻同屏動畫單位** → 轉原生。
- 確定要以 **Steam 首發** → 先評估 Tauri 包裝的體驗損失。
- 三個月後你還在**寫引擎**而不是**做遊戲** → 立刻轉 Godot。

## ADR-008 城市資料來源：上海街區與 CMAB

**決定**：遊戲以真實上海街區為場景。首批建築資料選用清華團隊的 CMAB 上海資料，已取得並校驗 Figshare 第 7 版上海檔案，生成 250 m 候選樣本；最終街區與遊戲適用性仍待確認。CMAB 不包含完成遊戲所需的一切資料，道路與其他來源另行選定和記錄。

- 資料發布頁與授權：<https://doi.org/10.6084/m9.figshare.27992417>，發布頁標示 CC BY 4.0。
- 論文：<https://doi.org/10.1038/s41597-025-04730-5>。
- 原始版本（Mendeley）：<https://doi.org/10.17632/b4t2wxhn2y.5>。
- 上海分區檔案清單顯示約 337 MB；資料版本、下載時間與實際檔案校驗資訊應隨取得結果記錄。

上海核心檔案包含 471,297 筆建築 Polygon 記錄，其實際 .prj 為 EPSG:3857；首個樣本轉換為 EPSG:32651 局部座標。詳見 [來源與校驗紀錄](../data/sources/cmab-v7/SOURCE.md)。CMAB 提供建築屋頂多邊形和高度、用途等推估屬性，不是現成的完整 3D 遊戲地圖，也不能預設高度、功能或道路可通行性準確。資料品質仍待檢查；室內、門、街道、碰撞與導航仍需補充。

**處理方式**：保留原始資料與來源資訊，擷取候選上海街區，將地理座標轉為局部公尺座標供引擎使用，記錄原點、投影及轉換方法。局部化不會改變其真實地理來源或授權要求。按真實資料品質檢查建築輪廓和高度，再生成可驗證的白模。

**授權與來源**：發布頁標示 CC BY 4.0，應保留作者、來源、授權連結、修改記錄與其他適用聲明；具體文件和任何額外條件在取得時核對。研究材料提到使用多種遙感與街景資料，因此需記錄上游來源並釐清適用範圍，不推定所有第三方權利均已清除。使用實際地理資料的發布及地理資訊規範，需按來源、用途和發布地另行核對，座標轉換本身並不提供豁免。

EmbodiedCity 是北京的 Unreal 模擬環境，其資料卡同時標示 Apache-2.0 與僅限非商業使用的存取條件；原始模型格式及可否改作、再分發未經確認，目前不作為本項目的城市素材。詳見 [素材授權邊界](asset-license.md)。

### 預計處理流程

1. 從官方資料集取得上海資料並記錄版本、來源、授權與檔案雜湊。
2. 檢查實際檔案格式、座標系、欄位和品質；以實際內容選出一小片候選街區。
3. 轉為可供遊戲讀取的建築輪廓與高度，保留來源關聯及座標轉換紀錄。
4. 補充道路、入口、碰撞與可達性；高度、用途等推估欄位不得直接當作已驗證實況。
5. 試做白模，測試斜俯視第三人稱尺度、遮擋與效能後再擴大範圍。

## ADR-010 引擎定案：維持 Three.js（屍群壓力測試，2026-10-29）

**決定**：維持 TypeScript + Three.js + Vite，不轉 Godot。

**背景**：ADR-007 曾訂下「同屏 > 100 隻動畫單位 → 轉原生」的重評條件。在寫任何生存循環之前，先用 `web/stress.html` 量測真實成本。

**測試條件**：Intel Arc 140V（16 GB 共享記憶體）、ANGLE D3D11、繪圖緩衝 2304×1224（DPR 1.6）、無陰影與後製、上海街區白模（63 棟樓、2.6k 三角形）。關閉視錐剔除，N 隻一律全部繪製；每列以自檢核對 draw call，不符即標記無效。

| 模式 | draw call | 400 隻時平均幀長 |
|---|---|---|
| InstancedMesh | 1（全場 5） | 未達上限（125 隻時 8.3 ms） |
| 獨立 Mesh | N + 4 | 100 隻時 8.9 ms |
| SkinnedMesh（3 骨） | N + 4 | 400 隻時 10.1 ms（約 99 fps） |

SkinnedMesh 一路到 400 隻都未觸發 20 ms 停止線（404 draw calls、23.4k 三角形）。以 60 fps 的 16.7 ms 預算計，仍有約 1.65 倍餘裕。

**否決**：轉 Godot。ADR-007 的 100 單位觸發條件在此硬體與此單位複雜度下不成立，該條件作廢。

**已知限制（這次沒量到的部分）**：

- 測試場景無陰影、後製、窗戶貼圖與街景細節；`main.ts` 完整街區的 draw call 基準尚未量測。
- 三骨是最小骨架；正式喪屍若用 20 骨，骨骼更新成本會上升。
- 筆電長時間執行可能降頻；每階只取樣 0.5–2 秒。
- 緩衝為 2304×1224，非 1080p 全螢幕。

**預算**：同屏 150 隻（軟上限 250）；draw call 預算 500。

**重評條件**：完整街景美術與 20 骨喪屍上線後，若 150 隻仍超過 16.7 ms/幀，再評估 LOD 或引擎。
